## 2. Invocation, capture and truthful outcomes

**SPECIFICATION.** The caller proposes arguments; deterministic code resolves protected account, payee, recipient, amount, target resource, claim form and scope from current authoritative records. User-supplied strings and source text cannot replace these trusted parameters. The resulting exact bytes and interpretation versions enter OperationIntent. C04 reserves money, capacity, potential duties and business conflicts before disclosure or external mutation. Gate expiry applies to the controlled transport event described in 02; neither an HTTP status nor a native exit code proves fulfillment.

**SPECIFICATION.** RawCapture/v1 is an ArtifactVersion with protected metadata: invocation/attempt identity; direction; endpoint and native account; media type; original length and digest; captured interval; capture sequence and missing ranges; header allowlist; credential generation; encrypted blob refs; retention/access/deletion scope. Authorization headers and cookies are omitted by structural field selection before persistence, with an omission marker; business content is retained under encryption and access policy. Capture occurs before the result is offered to a model. Streaming sequence gaps, truncated output, parser failure and missing final messages remain explicit. Exact request business bytes are reconstructible from the committed envelope; no claim that redacted credential bytes were retained. Free text is protected by default; numeric/enumerated fields and relationship metadata also require field-specific sensitivity/retention classification. Canonical sensitive record bytes use the kernel encrypted durable-blob path; GroupBody/JSONB, WAL, indexes, logs and backups must not retain accidental plaintext duplicates. Persisted full-text indexes are limited to explicitly admitted nonpersonal/nonconfidential material; protected content uses permission-filtered bounded in-memory lexical scanning with no persistent terms/snippets/query cache or spill. Any necessary plaintext relational projection has explicit purge/retention accounting and keeps deletion incomplete while it survives. Parser output is a derived Observation with the raw capture and parser version as dependencies. A hostile HTML page, e-mail, tool response or test log is data, including text that impersonates a system instruction.

**SPECIFICATION.** Default external attempt: one request, HTTP/1.1, fresh socket, no automatic redirect/retry/pooling, 30-second all-buffer gate window, request ≤1 MiB, response ≤8 MiB, decompressed response ≤8 MiB, depth-limited parse. A profile may set a shorter window or smaller bounds. A larger supported operation must be a separately reviewed profile with explicit reservations and the same gate semantics, never an invisible library default. Read retries: at most three total attempts in the causal episode with backoff 1/4 seconds and deadline check; observed 429 Retry-After defers without exceeding the deadline. Mutations retry only on positive proven-unsent evidence or a provider-specific current idempotency contract. Unknown effects retain holds and reconciliation work; changing tool or provider is not an escape from the business identity.

**DESIGN PROPOSAL.** Circuit breaker opens after three transport failures in five minutes, probes once after five minutes using a harmless admitted read, and resumes only on valid response/profile. Authentication failure, schema drift, unexpected redirect/destination, charge mode change or capture corruption quarantines immediately. A refusal records the unmet authority/standing/capacity predicate; a provider error records what was attempted; a timeout after possible send is unknown. All consume their actual causal resources. One provider's reported success and another's disagreement form a contested evidence set, not last-writer-wins truth.

**SPECIFICATION — added by the F2 join (R-D20, R-G07). **SPECIFICATION — the metered flip is a capacity event, not only a money and policy event (R-G07).** Enabling credits **drops the prompt-cache lifetime from an hour to five minutes**. ### 9.1 The transport boundary, request identity and what the gate can see

**SPECIFICATION.** IC-MAIL-OUT is an ordinary consequential HTTP attempt and takes the full P1–P7 path of [02 §6.2](02-authority-recovery.md#62-ordered-preparation-release-and-send-claim). It sits **inside** the controlled-egress boundary of [02 §7.2](02-authority-recovery.md#72-gate-and-connector-profile): the connector process runs under G, receives frozen request bytes through the protected local pipe, and its packets leave only through G's dedicated per-attempt namespace/interface under the default-deny forward chain with the absolute nftables cutoff. There is no second route: the mail connector has no shell, no model, no DNS of its own, no redirect following, no SDK, no connection pool and no production filesystem. A message that C04 has not released cannot reach the provider, and a message C04 has released reaches exactly one pinned destination.

**SPECIFICATION — three distinct identities, never conflated.** (1) The **company attempt identity** `{operation_ref, attempt_index}` in the committed SendClaim, which is what G arms against and what the local durable attempt ledger consumes once. (2) The **request identity** `request_digest` over the frozen executable bytes, which is what binds the envelope to what was actually emitted. (3) The **provider message identity** returned in the response or appearing in later events, which is the provider's own name for its object and has no authority in this company. A join between (1) and (3) is an evidence relation recorded by C06; it is never an equality, and a missing join is an unknown, not an absence of effect.

**SPECIFICATION — what the gate can and cannot see.** G's nftables hook evaluates a kernel buffer on the attempt interface against destination, protocol, port and absolute time. It cannot see the recipient address, the message body, the stream, the consent basis or any suppression state, because those exist only inside the TLS session it is forwarding. **Therefore no recipient-level or consent-level rule may be specified at the gate**, and any design that claims one is wrong about this boundary. The gate bounds *when and to whom the connection may exist*; it does not bound *what the message says*. That separation is the reason sections 9.2 and 9.5 place their enforcement where they do.

### 9.2 Where suppression and eligibility are actually enforced

[Architecture selection §4](../02-architecture-selection.md#4-control-admission-and-external-effects) requires that a connector promising stricter suppression enforce it **at the relevant provider boundary**. This adapter promises a suppression that is strictly narrower than the provider's, so it has three enforcement points with different visibility, and the promise is discharged only by the conjunction of all three.

| Point | When it runs and what it can see | What it decides | What it cannot do |
|---|---|---|---|
| **E1 company authority (C04, at P1 and re-read at P3)** | Recipient identity and verified relationship, consent basis with its source and date, company `Suppression` records, contact-frequency and population `ConflictClaim`s, the admitted mail form, the connection's provider-terms Observation | Refuses preparation or release. This is the only point that can stop a message before it exists | See provider-side suppression changes later than its last admitted read; recall a released message |
| **E2 provider boundary (the provider's own suppression handling for that server/stream)** | The provider's recorded suppressions for its own server and streams (SOURCE CLAIM: a suppressions API is documented — [suppressions API](https://postmarkapp.com/developer/api/suppressions-api), 2026-09-12). **UNKNOWN (admission check):** whether the provider blocks an accepted request to a suppressed address, and with what error, is not established in this package | Is the last boundary before the provider's own transmission | Consent. A recipient's **absence** from the provider's suppression list is not permission, is not a relationship, and may never be read as one |
| **E3 gateway G** | Destination IP/port and current kernel time only (9.1) | Whether the connection may exist at all within the window | Anything about recipients, content or suppression |

**SPECIFICATION.** The decision is the **conjunction**: a send proceeds only if E1 permits *and* the current admitted provider-suppression observation does not deny. The provider's permission never widens E1's decision; a deny at either point is a deny, and the refusal records which predicate was unmet. The provider-suppression observation used at P3 must be no older than **300 s** and is re-read immediately after any bounce or complaint event for that recipient or after any connection pause/resume; a stale, failed or unparseable observation is a refusal, not a permit. Company `Suppression` records are authoritative and permanent within their scope and are never removed because the provider's list no longer contains the address.

**SPECIFICATION — provider eligibility is a separate predicate from company authorization, and it is checked first.** `ProviderEligibility` is a profile predicate evaluated before P1 over {mail form, message stream, consent basis and its evidence, audience derivation, unsubscribe handling}. **SOURCE CLAIM:** the provider's terms, effective 2024-12-10, require permission-based lists and restrict unsolicited messages ([terms of service](https://postmarkapp.com/terms-of-service), accessed 2026-09-12). **INFERENCE (carried from the 2026-09-12 inspection and F-integration-04, not new):** exact founder authorization of content and recipients does not by itself make an outreach eligible for this adapter; a campaign whose audience is derived rather than opted in fails `ProviderEligibility` even when the company grant, the content and the amount are exact. The refusal is recorded as an unmet provider-terms predicate naming the clause relied on, is visible to the owner, and routes the work to IC-HUMAN or to an explicitly admitted alternative route — it is never silently retried on another adapter, and changing tool does not change the business identity (section 2).

**UNKNOWN (admission check) — actual account facts that remain unknown and are not invented here:** whether an actual account exists or would be approved for a custom API client; the account's monthly allowance and whether charges above it apply automatically; the account's eligible message streams; the applicable law, principal and recipients; the current provider IP ranges used for webhook delivery; and whether any of the terms clauses is modified by an actual agreement. **SOURCE CLAIM:** the terms address account credential sharing, approved API access, third-party application consent, unsubscribe handling and extra charges above the monthly allowance ([terms of service](https://postmarkapp.com/terms-of-service), 2026-09-12); that they *address* these subjects is what the source supports. What they permit **for this company** is an account-admission question, and this section states no answer.

### 9.4 Inbound provider events: identity, deduplication, retention

**SOURCE CLAIM ([webhook overview](https://postmarkapp.com/developer/webhooks/webhooks-overview), accessed 2026-09-12; publication date not established).** The provider documents no HMAC webhook signatures; its recommended protection combines HTTPS Basic Authentication with current provider IP allowlisting, endpoint verification is a separate feature, and the page describes retrying failed processing. **UNKNOWN (admission check):** the retry count, the retry horizon, whether a retried delivery is byte-identical to the original, and the current IP ranges.

**SPECIFICATION — the ingress receiver.** Inbound events terminate at the admitted company ingress boundary, never at A's control plane directly. The receiver holds no grant, no company credential and no model; it authenticates, stores and acknowledges, and nothing else. Its acknowledgement means exactly *received and durably staged at this boundary* — never accepted, understood, believed or acted upon, and never a discharge of any customer duty. It acknowledges only after the raw capture and the deduplication key are durably written; if that write fails it does not acknowledge, and provider redelivery is the recovery path.

> **OPEN PLACEMENT DECISION, deliberately not taken here.** Which admitted boundary hosts the receiver — the Cloudflare Worker of IC-PUBLIC, or a narrow inbound listener under G — is an architecture placement with different exposure, quota and recovery consequences, and it is the orchestrator's to decide. Both candidates must satisfy the constraints in this subsection unchanged. This section specifies the contract, not the host.

**SPECIFICATION — origin authentication and its exact limit.** A unique high-entropy Basic credential per connection and endpoint, issued from the credential boundary, rotated on any suspicion and on connection revision; the configured endpoint URL and the `Authorization` header are excluded from logs, captures and artifacts by structural field selection with an omission marker (section 2); TLS terminates at the ingress boundary under our own certificate; the peer address is verified against the current admitted provider range through explicit trusted-proxy handling, with the range maintained as an admitted dependency that expires. **INFERENCE:** this is a shared-secret claim, so a leaked credential, a stale allowlist or a provider-side compromise forges an event that our checks accept; provider endpoint verification is an availability feature and is not message authenticity. **SPECIFICATION, following from that limit:** no inbound event may by itself produce a consequential effect. An authenticated event may (a) record an `IntegrationObservation`, (b) apply or extend a company `Suppression`, or (c) create a case or duty for qualification. It may never release money, discharge a duty, close a complaint, accept an outcome or widen any permission. Effect (b) is permitted unreconciled because suppression only ever restricts — and the resulting exposure is stated rather than hidden: **a forged complaint stream can deny service to a legitimate recipient**, which is detected by reconciliation against the admitted provider read route and is an incident, not a silent state.

**SPECIFICATION — event identity.** The deduplication identity of an inbound event is

`EventIdentity = (company_id, connection_ref, provider_server_identity, record_type, event_occurrence_key)`

enforced as a unique constraint in the ingress inbox, with these four rules.

1. **Distinct per event kind.** `record_type` is part of the identity, so a delivery, a later bounce and a later complaint for one provider message are three distinct events with three distinct effects. Deduplicating on the provider message identifier alone is prohibited: it would collapse exactly the events that matter most.
2. **Stable under provider retry.** `event_occurrence_key` is taken from the provider's own event-specific identifier for that record type where one exists, and otherwise from a digest over the event's content fields **whose invariance under redelivery was positively established at admission**. A field whose retry-stability is not established is excluded from the key and retained as observation payload only. **UNKNOWN (admission check):** the per-record-type field paths and their retry-stability are not established in this package; each is bound and tested at admission, and this section deliberately names no field.
3. **Collisions are contested, never discarded.** Two events sharing an identity but differing in content are not a duplicate: both raw captures are retained, the observation is marked `contested` (section 1), and the meaning is resolved through the admitted provider read route. Silently dropping the second is prohibited.
4. **No identity, no effect.** A record type for which no stable per-event identity can be bound at admission is admitted only in **reconcile-only mode**: its events are hints that schedule a provider read and a `SourceCursor` reconciliation, and they produce no business effect of their own. Inventing an identifier to make such a type usable is prohibited.

**SPECIFICATION — uniqueness scope and retention.** The scope is per company, per connection and per provider server, so re-registering an account or admitting a second server creates a new scope and cannot collapse two accounts' events; a connection revision that changes the scoped provider identity invalidates incompatible prepares (section 1). The deduplication key is retained for the **longer** of: the life of every operation, duty and dispute it bears on, plus their reconciliation; and the observation's own admitted retention. It is explicitly **not** a sliding window that may expire while the related duty is live, and its retention is accounted in `DeletionScope` like any other record.

**SPECIFICATION — lost responses and expired windows never justify a resend.** On the inbound side, a lost acknowledgement means the provider may redeliver; a redelivery meets the unique constraint and receives the same acknowledgement with no second effect. If the deduplication index itself is lost or rebuilt, re-imported events fall back to the recorded business effect for that `(provider message, record_type, occurrence)` — already-applied is a no-op — and any event whose prior application cannot be established enters reconcile-only mode. On the **outbound** side, a lost send acknowledgement is `unknown_effect` under [02 §9](02-authority-recovery.md#9-operationattempt-state-cancellation-retry-and-outcomes) and **there is no blind resend and no automatic retry**, because this profile has no idempotency contract (9.1). What happens instead: the operation retains its holds and its potential obligations; C04 reconciles by reading the provider's own record for that attempt through the admitted read route, keyed by the opaque per-attempt value carried in the message's metadata or tag (9.5); if that read resolves to exactly one message the effect is determined, and if it does not, the operation stays `unknown_effect` with an owned reconciliation duty and the owner is told so in those words. **UNKNOWN (admission check):** whether the provider's read route can resolve an opaque attempt key to at most one message is not established here. If admission shows it cannot, this adapter is admitted only for mail forms whose duplicate is tolerable *or* whose send requires human confirmation — not for forms whose duplicate creates a second business effect.

### 9.6 T-R3 conformance for this adapter

[T-R3](../../registers/review-findings.json) requires delayed first transmission, retries and delayed provider acceptance to be bounded separately, and grants and operator views to expose the gateway generation, the first-send deadline, cancellation/expiry semantics and the residual revocation window. This adapter conforms as follows, all of it inherited mechanism rather than new machinery.

| T-R3 obligation | This adapter (SPECIFICATION) |
|---|---|
| Gateway generation fencing | The SendClaim binds `gateway_instance_id` and `gateway_boot_id`; a claim from an old boot cannot execute, and the claim is consumed once at the registry and once in G's local durable attempt ledger ([02 §6.2](02-authority-recovery.md#62-ordered-preparation-release-and-send-claim)) |
| First-transport deadline | 30 000 ms from bounded release time, capped by the earliest grant, prerequisite, account and credential expiry; compiled into the absolute nftables cutoff with the clock margin of [02 §7.3](02-authority-recovery.md#73-clock-admission-and-margin) |
| A paused gateway retains no indefinite first invocation | The cutoff is absolute wall-clock at the packet hook, not a process timer. A connector paused before arming, after its userspace check, before the socket write or mid-buffer and resumed past the cutoff is dropped at the hook; bytes admitted before the cutoff may still arrive later and are classified as possibly applied ([02 §7.4](02-authority-recovery.md#74-partial-sends-revocation-and-observed-limits)) |
| Retries bounded separately | Zero automatic retries for this adapter (9.1), so the retry interval is not an additional exposure. A new attempt requires positive proven-unsent evidence and a newly authorized deadline, never a replayed one |
| Delayed provider acceptance bounded separately — and honestly unbounded | Passing the packet cutoff does **not** bound when the provider accepts, transmits or delivers. **The residual revocation window for a mail effect does not end at the gate cutoff**; it ends only at an observed provider outcome or an explicitly declared unknown.
